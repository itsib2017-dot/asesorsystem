## 1. Vision

Give every BNSP assessor (*asesor kompetensi*) a single web workspace that takes a messy, real-world certification batch — public Google Drive folders, a completeness spreadsheet, paper forms, presentations, and written tests — and turns it into a defensible, auditable assessment record ending in a correct **FR.AK.05 Laporan Asesmen** pack for the TUK/LSP.

The system does the heavy, repeatable work (ingest, classify, extract, compare, draft) and leaves every judgement to the assessor. **AI recommends; the assessor decides.** That sentence is the product's core principle, not a slogan: it follows directly from the BNSP forms themselves, which instruct the assessor to use *professional judgement* when deciding whether an essay answer is acceptable. For certificate names, an AI jury proposes the verdict — the assessor confirms it (v1.2, decision D10); the KTP is the authority for the name (v1.3, decision D6). In v1.4 (D16) the AI also does the judging work on the roll-up: it judges VATM sufficiency of the evidence per unit and recommends K/BK — the assessor confirms or overrides. The judging work is the AI's; the decision stays the assessor's.

## 2. Problem statement

Today an assessor's batch looks like the real November 2026 batch that grounds this project (see §6):

1. **Messy intake.** Evidence arrives as public Google Drive links whose folder structure is unpredictable and partly re-shaped by the TUK: inconsistent file names (`DIT_[Name].pptx` vs `TUGAS PRESENTASI DIT [Name].pptx`), duplicate markers (`(1)`, `-v2`, `-2`), double extensions (`.jpg.jpeg`), generic names (`KTP Image`, `Foto Image`), WhatsApp camera filenames, and a completeness spreadsheet whose assessee list lives inside a single cell.
2. **Manual completeness checking.** The assessor (or LSP admin) tracks APL.01 / APL.02 / KTP / ijazah / pas foto / CV / sertifikat pelatihan / portofolio in a spreadsheet. Gaps are discovered late, and unsigned Word files are sent where signed scans were expected.
3. **Manual comparison at scale.** For the structured-activity route the assessor must read 20+ DIT papers (FR.IA.04A) and spot copy-paste between candidates by eye. For the written test the assessor must grade every FR.IA.06C answer against the FR.IA.06B master key, per question, per candidate — and again spot copying between candidates.
4. **Identity risk on the certificate.** The name printed on the BNSP certificate follows the data submitted. If the name on the surat tugas, APL.01, and KTP disagree — titles, degrees, clan/family names, spelling — the certificate is printed wrong and fails verification. Today this matching is done by eye, if at all. In v1.2 the system runs local OCR on the KTP image and an AI jury adjudicates the four sources (KTP OCR text vs APL.01 vs surat tugas vs ijazah); the jury's verdict becomes the certificate name only after the assessor confirms it (decision D10). Decided in v1.3 (D6): the KTP is the authority — the certificate name is the KTP name verbatim, word for word; the other sources are compared against the KTP and any discrepancy resolves to the KTP spelling. Worked example: surat tugas says "Declan Rice P." but the KTP says "Declan Rice Pangabean" → the final certificate name is "Declan Rice Pangabean".
5. **No audit trail.** AI-style prompting is currently done ad hoc in a chat window (the user's two prompts). There is no stored prompt version, model version, input, or output — nothing a surveillance audit could replay.
6. **The final report is assembled by hand.** FR.AK.05 — the per-assessor, per-batch report submitted to the TUK/LSP — is compiled from scattered notes, and the handoff to the LSP pleno (which alone makes the certification decision) is implicit.
7. **One flat folder, several assessors, no separation.** A single long Drive folder can hold several assessors' candidates with no per-assessor subfolder. Today nobody can tell, from the folder alone, which files belong to which assessor — the split has to be reconstructed from the group sheet and the surat tugas.
8. **The master key password is held outside the system.** Each scheme's 06B ships with a PASSWORD Excel file holding the key password. The repo's SKEMA copy of the 06B blank is OLE-encrypted (it does not parse as a normal `.docx`); the working AK3U key copy is a plain OOXML docx that opens directly (verified 2026-11-18, `research/06b-key-structure-2026-11-18.md`) — both copies exist. The key can only be used if the assessor supplies the password at run time (key-upload step) — and the password must never be stored, logged, or recorded anywhere.
9. **Signatures are applied off-system, or not at all.** The blank forms require the assessor's signature (AK.05, AK.02, AK.01, AK.06, AK.07, FR.IA.04B, Berita Acara) — today the assessor prints, signs by hand, and rescans, or sends the document unsigned. There is no record of whose signature was applied, or when. In v1.2 the assessor uploads a signature once (decision D11); the system applies it at sign-off and records signature + timestamp on every document.

## 3. What the system is — and is not

| It is | It is not |
|---|---|
| An assessor's workbench for one batch at a time | A candidate-facing exam platform (candidates do not log in to sit tests here in v1) |
| OHSE-first (Ahli K3 Umum), multi-scheme by default (D17): every scheme registers its own manifest — file set, question counts, assessment/decision rules, prerequisites, registration requirements. AK3U's values are AK3U's manifest only (e.g. Petugas K3 has a different file set; its values are unknown and never invented) | An AK3U-only tool; any scheme's file list, question counts, rules, or prerequisites hard-coded or assumed from AK3U |
| A recommendation engine: coverage matrices, gap questions, grading drafts, similarity flags | An auto-grader or auto-decider. No verdict, no K/BK decision, and no plagiarism verdict is ever produced without assessor confirmation |
| A Drive-ingestion and document-classification pipeline | A Drive scraper. Ingestion uses the official Drive API v3 only |
| The producer of the assessor's final deliverables (FR.AK.05 pack, see §7) | The certification decision-maker. FR.AK.05 is a *recommendation* to TUK/LSP; the LSP pleno decides certification and BNSP issues the certificate |

## 4. Target users

| User | What they do in the system | What they never do |
|---|---|---|
| **Asesor** (assessor, holds BNSP No. Reg MET) | Owns a batch: ingests Drive folders, reviews completeness, runs DIT and written-test analysis, confirms grades and names, signs FR.AK.02/AK.05 | Never has a decision auto-applied; never sees another assessor's candidates unless assigned |
| **Ketua Tim Asesor** (lead assessor) | All assessor powers, plus consolidates assessors' AK.05 reports for one batch and resolves cross-assessor conflicts | Does not override another assessor's per-candidate K/BK without that assessor's re-confirmation (logged) |
| **LSP admin** | Creates schemes, batches, and assignments; configures form-version mappings and thresholds; manages users; receives the AK.05 pack | Does not grade, does not change assessor verdicts |
| **TUK viewer** | Read-only view of the batches at their TUK and the submitted AK.05 pack | No editing, no grading, no access to other TUKs' batches |
| **Auditor (read-only)** | Read-only access to audit logs, prompt/model versions, and exports for surveillance audit | No editing, no data export of KTP/NIK material |

Candidates (*asesi*) are **not** users in v1. Their data enters via Drive/Sheets and via assessor upload. A future candidate portal is out of scope (see PRD §11).

## 5. Scope — v1 in one paragraph

v1 covers one full batch lifecycle: **scheme registration (once per scheme — file manifest, question counts, assessment rules, prerequisites, registration requirements; D13/D17) → batch setup (per batch only: 1–2 Drive links + Kelompok Asesi; D13) → Drive/Sheet ingest → completeness & AI name-jury identity review (local KTP OCR + verdict + assessor confirm) → route assignment (structured activity FR.IA.04A/04B, or portfolio FR.IA.08→09→10, plus observation/written-test instruments as configured) → AI-assisted DIT analysis (coverage matrix, gap questions, 13-question bank — count is the scheme's manifest value, default 13 for AK3U) → written-test grading (FR.IA.06B vs 06C, rules-first + LLM partial credit) → cross-candidate similarity flagging (DIT and written test, numeric thresholds + evidence details, D19) → per-candidate decision FR.AK.02 (AI judges VATM sufficiency per unit, assessor confirms — D16) → FR.AK.05 report pack (assessor signature applied at sign-off) → handoff to TUK/LSP/pleno.** Everything outside that lifecycle — candidate self-service, payment, scheduling, certificate printing, BNSP submission — is out of scope for v1. AK3U is the example scheme only: the system supports many schemes, each with its own manifest (D17); one master key per scheme name (like "Schema A" in the reference Test Grader app).

## 7. Final assessor deliverables — the end products

**Origin** = whether the artefact is a **system output** (generated/filled in the system), an **ingested input** (arrives as a file and is stored/linked, not generated), or **hybrid** (partly generated, partly signed/filled outside). **Recipient** = who receives the finished artefact. ## 9. Canonical rules the whole system must obey

These are non-negotiable and appear in every Group A–C document. **Rule 24 is the governing rule: no value is hard-coded anywhere (D21)** — every other rule's values live in config.

1. **DIT = Daftar Instruksi Terstruktur** (FR.IA.04A). Never "Tertulis".
2. **FR.IA.04B (official)** = Penilaian Proyek Singkat atau Kegiatan Terstruktur — presentation assessment. The form is real and verified (v1.4, D14): 4 Kelompok Pekerjaan covering all 13 units, 13 built-in questions (one per unit), Ya/Tidak per KUK, binary recommendation Kompeten/Belum Kompeten; its evidence is the DIT task + presentation. The user's 13-question bank is a **separate artefact**; question counts are per-scheme manifest values (default 13 is AK3U's value — D17).
3. **Decision is binary: K (Kompeten) or BK (Belum Kompeten).** "Kompeten Bersyarat" is **not** a decision value, a status, or a recommendation — it does not appear in the AK3U scheme document (§9.3.4) or in the 04B form, which only offer Kompeten / Belum Kompeten (D15, v1.4; OQ-03 closed).
4. **FR.IA.09** is the interview form inside the portfolio route (IA.08 → 09 → 10), not the route itself.
5. **Form-suffix mapping is per-scheme configurable, as part of the scheme manifest (D17).** Under MUK 2023, 06A = soal, 06B = kunci, 06C = jawaban — but other LSP documents swap suffixes. Never hard-code. Each scheme's manifest states which forms exist, their names/suffixes, which are required vs optional, and which instruments the scheme uses.
6. **Scheme data is config — per-scheme manifest (D17, v1.4).** The system is multi-scheme by default, not AK3U-only. Every scheme registers its own manifest: **file set** (which forms exist, names/suffixes, required vs optional, instruments); **question counts** (04B built-in count, 06A essay count, question-bank default count — all per-scheme, never hard-coded to 13); **assessment/decision rules** (VATM is the rule in the AK3U scheme document §9.3.3–9.3.4 — other schemes' rules come from their own scheme documents, never a global hard-code); **prerequisites** (entry education/experience combinations per scheme); **registration requirements** (evidence list per scheme). The AK3U values (13 questions, SLTA+3yr / D3-D4-S1+2yr / S2-S3+1yr, the AK3U evidence list) are AK3U's manifest values ONLY — e.g. Petugas K3 has a different file set, and its values are unknown and never invented. The AK3U 13-unit list (Kepmenaker 38/2019) is the default seed for AK3U, not a constant; the active packaging is whatever the LSP's current scheme document says.
7. **Similarity is a flag, never a verdict.** VATM "Asli" failures are for the assessor to judge; no auto-fail, no auto-merge of identities.
8. **Identity is AI-jury adjudicated, human-confirmed; the KTP is the authority (D6, decided v1.3; D10).** Local OCR reads the KTP image; the AI jury compares the other three sources (APL.01, surat tugas, ijazah) against the KTP (OCR text) and issues a verdict — match / mismatch-resolved (with a proposed certificate name) / needs-human — with reasoning, evidence spans, and OCR confidence. **The certificate name is the KTP name verbatim, word for word**; a mismatch-resolved verdict always proposes the KTP spelling — the jury never invents or picks a spelling from another source, and it expands abbreviations using the KTP only. Worked example: surat tugas says "Declan Rice P." but the KTP says "Declan Rice Pangabean" → the final certificate name is "Declan Rice Pangabean". The verdict becomes the certificate name only after the assessor confirms it (one tap) or overrides it with their own value. Never auto-merge or auto-correct names; every step is audit-logged. Needs-human when the KTP itself is unclear or OCR confidence is low.
9. **PDP (UU No. 27/2022):** NIK/KTP number, address, phone, photos are personal data. **NIK/KTP images never go to an LLM** — redact before any LLM call. KTP OCR is local (Tesseract); only redacted OCR text (name fields) reaches the AI jury. KTP originals live only in a private, RLS-protected Storage bucket with audit-logged access.
10. **AI output is a recommendation.** Essay grading is rules-first + LLM partial-credit; the assessor confirms every verdict (professional judgement, explicit on FR.IA.06).
11. **Model answers are assessor-only.** The system may generate model/expected answers for the 13-question bank so the assessor has something to judge against. Model answers are labelled as such, shown only to the assessor, and are **never** stored as candidate evidence and **never** shown to a candidate as their answer. The system never drafts a candidate's answers (VATM "Asli").
12. **Completeness gate before analysis.** DIT analysis must not run until the required inputs for that candidate are complete (FR.IA.04A + presentation transcript/recording + profile). If anything is missing, the system lists what is missing and defers analysis — it never invents coverage.
13. **Prompts are versioned, registered artefacts.** The assessor's two prompts live as versioned templates (`research/prompts/` verbatim; code templates per scheme/form in the build), never as unversioned chat text. Every AI run records prompt key + version + model version.
14. **The GitHub repo is never a data store.** The repo is public and holds assessee personal data (see §6). The system must never read from, write to, or depend on the repo for candidate data. Originals live in Drive (source) and in the private Supabase bucket (working copies); only extracted text + metadata live in Postgres.
15. **The 06B key password is run-time only (D12, v1.3).** Each scheme's 06B ships with a PASSWORD Excel file holding the key password; the password holder is the assessor, who supplies it at run time for that grading session (key-upload step). The password is never stored, never logged, never committed, and never recorded in any doc, note, or memory file. Two copies exist: the repo's SKEMA copy of the 06B blank is OLE-encrypted; the working AK3U key copy is a plain OOXML docx that opens directly. The working key has 13 answers in one table, written as prose (acceptable points embedded in sentences, not pre-split lists), plus 8 embedded images — extraction must flag embedded images rather than silently dropping them (`research/06b-key-structure-2026-11-18.md`).
16. **Export rule (D8, decided).** AK.05 is exported as PDF + DOCX. Every other generated document is DOCX only. In-app review records stay in-app. Tabular data extracts (audit-log extract, completeness matrix) may additionally be XLSX as data, not documents.
17. **Assessor signature (D11).** The assessor uploads a signature (scan/photo PNG or drawn signature) at onboarding/profile; it is stored in private Storage (RLS, audit-logged). It is applied to generated documents that carry an assessor signature block in the blank (AK.05, AK.02, AK.01, AK.06, AK.07, 04A, 04B, 07, 08, 09, 10, APL.01, APL.02, Berita Acara) at sign-off/finalise only, never on drafts; each application records signature + timestamp; AK.05 submit is blocked while the assessor has no active signature; replacing a signature keeps old versions (past documents keep the signature they were signed with); another assessor's signature can never be applied to your documents. The assessor also fills the LSP-side fields on APL.01 (§3.1 recommendation) and APL.02 (review + recommendation), recorded in-app. Assessee signature blocks are out of scope for generation (wet signatures on scanned originals). No assessor signature is applied where the blank has no assessor block (AK.03 (no signature block in the blank), AK.04 (asesi signature only), MAPA.02 (no signature block), VA (no signature block); MAPA.01's relevant-person confirmation table (incl. a Lead Asesor row) is UNCONFIRMED (OQ-17) — see §7 signature note).
18. **Low OCR confidence means needs-human.** If KTP OCR confidence is below the configured threshold, the jury issues no verdict — the candidate goes to human review. The threshold value is **UNCONFIRMED** (OQ-16).
19. **Written-test judging shape (D7, v1.3) + roll-up (D16, v1.4).** Per-question verdicts Benar / Sebagian / Salah, each with a Bahasa Indonesia explanation, plus a per-student error summary ("Ringkasan Kesalahan" — which question numbers were wrong per student). The plagiarism analysis is a separate qualitative report (status Bersih / Waspada + reasoning), never a numeric plagiarism verdict. No overall percentage is shown as the decision. **Roll-up (D16, replaces the v1.3 default):** the AI judges VATM sufficiency of the evidence per unit and recommends K/BK; the assessor confirms or overrides. The rule is the AK3U scheme document §9.3.3–9.3.4 — evidence meeting VATM → Kompeten, otherwise Belum Kompeten — with no numeric pass mark anywhere in the scheme.
20. **Upload flow (D13, v1.4).** A scheme and its scheme-level forms (06A, 06B) are registered **once per scheme**. Per batch the assessor supplies only: 1–2 Google Drive links (participants data and/or DIT tasks / portfolio) + the Kelompok Asesi (Drive link or .xlsx). Filled per-candidate copies of 04A/04B/09 are ingested **from the Drive folder**; direct file upload is only a fallback. **Blank forms** (registered once per scheme) are distinct from **filled copies** (ingested per batch) — never present the scheme setup again at batch time.
21. **Provider-agnostic, free-first, BYOK (D18, v1.4 — replaces the GPT-4o-mini-primary decision).** The user brings their own key and picks the provider — Anthropic, OpenAI-compatible, Gemini, OpenRouter / OmniRouter / 9Router, Nvidia NIM, etc. Provider + base URL/gateway + model + key are runtime config. Keys are stored locally (browser) and sent per request, never logged, never committed. Free tiers are usable. Grading/jury verdicts stay at temperature 0 (deterministic); temperature is a per-prompt config value (Moza's Test Grader app uses 0.9 as its own default — not the grading default).
22. **Similarity thresholds are numeric, with details (D19, v1.4).** Similarity flags use per-scope numeric thresholds **with** evidence details (spans, shared unique errors). The threshold **values are UNCONFIRMED** (to be calibrated on real batches or set by Moza) — no number invented. The qualitative Bersih/Waspada report stays as the human-facing summary alongside the numbers.
24. **Zero hardcoding — config-based throughout (D21, v1.4; governing rule).** NO HARDCODED VALUES AT ALL, FOR ANYTHING. Every value that varies by scheme, org, or deployment comes from config: scheme names and file manifests, question counts (never a literal 13 in code — 13 is only the AK3U manifest's value), decision/assessment rules, thresholds, prerequisites, requirements, roles, export formats, providers, models, temperatures, UI labels. Wherever a doc states a literal AK3U value, it is the AK3U manifest/config value, never the system default. If a fallback is needed for a missing config, the fallback itself is a config value, not a code constant.
