## 0. MVP definition (the line that decides scope)

**MVP ships:** create batch → paste public Drive link → paginated async ingest → **multi-assessor triage (split one flat shared folder across assessors)** → completeness triage (APL.01/APL.02/KTP/Ijazah/Pas Foto/CV/Sertifikat Pelatihan/Portofolio) → identity check (**KTP read by local OCR; the AI name jury compares KTP vs APL.01 vs surat tugas vs ijazah and recommends match / mismatch-resolved / needs-human; the assessor confirms or overrides — the jury never decides alone; **v1.3, D6 decided: the KTP is the authority — the certificate name is the KTP name, verbatim, and any discrepancy resolves to the KTP spelling**) → DIT analysis (FR.IA.04A coverage matrix + gap questions + question bank — count from the active scheme's manifest, 13 for AK3U; **gated — never runs on incomplete inputs**; the official FR.IA.04B form shows its built-in questions per Kelompok Pekerjaan with the DIT deck as evidence, v1.4 D14) → written-test grading (FR.IA.06B key vs 06C answers, per-question correct/partial/incorrect each with a Bahasa Indonesia explanation, plus a per-student error summary (Ringkasan Kesalahan) and a separate qualitative plagiarism report (Bersih / Waspada); **no overall percentage as the decision**; **06B key unlocks with a runtime-supplied password, never stored** — v1.3, D12: the AK3U working key is a plain docx, the repo's SKEMA blank is encrypted, both copies exist; model answers assessor-only) → cross-assessee similarity report (flag only — numeric thresholds + evidence details, v1.4 D19) + **combined Markdown report (grading + similarity, one document, Bahasa Indonesia)** → per-assessee K/BK decision (AK.02 — **the AI judges VATM sufficiency per unit and recommends K/BK, the assessor confirms or overrides, v1.4 D16**) → FR.AK.05 draft + **true preview** + **PDF/DOCX export** + accept/return handoff. **Scheme registration + manifest (v1.4, D17) is a P0 building block:** each scheme registers its file set, question counts, rules reference, prerequisites, and registration requirements — AK3U is one manifest. **Per-batch intake is short (v1.4, D13):** pick the registered scheme → paste the Drive link(s) → supply the Kelompok Asesi → go. **Provider Settings (v1.4, D18):** provider + model + key are user-supplied runtime config (BYOK, free-first). **Config-based throughout (v1.4, D21):** no hardcoded values at all — every scheme/org/deployment value comes from config. **Assessor signature:** uploaded once at onboarding / in Pengaturan → Profil (scan/photo PNG or JPG, or drawn), applied at sign-off to the documents that carry an assessor signature block; AK.05 submit is blocked with no active signature. **Export rule (D8 decided):** AK.05 = PDF + DOCX; every other generated document = DOCX only; tabular data extracts may additionally be XLSX (data, not documents).

**Explicitly NOT in MVP:** candidate login, public pages, **FR.IA.09 portfolio-route interview pipeline (stays P1 — see the decision below)**, MC grading (FR.IA.05), MCP server, Sveltia-style CMS, payment, notifications (WA/email), pleno/BNSP-submission tracking beyond "AK.05 handed to TUK/LSP".

**Decision — FR.IA.09 stays P1 (v1.1, approved default D4).** Reason: the MVP must first prove the training route end-to-end on a real live batch; the portfolio route is a second pipeline (IA.08 desk evaluation → IA.09 interview questions from IA.08 gaps → IA.10 third-party verification) with its own prompt, and building both routes at once doubles the AI surface before the first route is validated. **Repo evidence that it is real work, not a hypothetical:** the repo now contains completed portfolio-route examples (3 × FR.IA.08/09/10 in ASESMEN (DONE)/) and the full blank Verifikasi Portofolio MUK for all three schemes (SKEMA/). **Promotion trigger (named decision, not a vague "later"):** FR.IA.09 moves into the next batch's scope (P1) as soon as the MVP has run one live training-route batch, or earlier if the LSP assigns a batch whose assessees are experience-based — whichever comes first. The ERD already models the portfolio tables (doc 04 v1.1), so promotion is pipeline + prompt + UI work, not a schema redesign.

  - M0.5 Job-queue skeleton: `jobs` table (`id, type, status, payload, progress, error, attempts`), a worker entry point runnable locally (`pnpm worker:dev`), enqueue endpoint returning immediately. No real work yet — a "hello" job that completes.

Upload limits (file types PNG/JPG, max size) are config values set at deployment — no fixed numbers are asserted here. No new secrets.
- **Exit criteria:** `pnpm dev` runs; login works for two roles; RLS test proves assessor A cannot read assessor B's batch; a queued job completes end-to-end; CI green.

## 3. Phase 1 — Ingest & completeness (Weeks 3–5)

**Goal:** turn a messy public Drive folder into a trustworthy completeness picture.

- **Milestones:**
  - M1.1 Drive client: API v3 + API key; `files.list` paginated (pageSize 100, `nextPageToken`), recursive crawl, persisted raw tree before any download; `files.export` for Google Docs/Sheets, `alt=media` for binaries; per-file jobs; resume from checkpoints; exponential backoff on 429/403.
  - M1.2 Classifier: MIME + filename heuristics + parent-folder name + content sniffing; normalisation (case, `_`/`-`/spaces, `APL` vs `ApL`, `(1)`/`-2`/`-v2` duplicate markers, double extensions like `.jpg.jpeg`, generic names "KTP Image"/"Foto Image"); `unmatched/` review queue with manual mapping.
  - M1.3 Extraction: text-layer PDF first (`pdfjs-dist`), DOCX via `mammoth`, XLSX via `exceljs`; scanned PDF/image via Tesseract 5 (`ind+eng`); per-file extraction method + confidence stored; low-confidence flagged in UI. LLM-vision fallback only for flagged pages, assessor-reviewed, never silent default.
  - M1.4 Completeness matrix UI: per-assessee × doc-type grid matching the real "Kelompok Asesi" sheet columns (APL.01, APL.02, KTP, Ijazah, Pas Foto, CV, Sertifikat Pelatihan, Portofolio: Sertifikat BNSP / Surat Keterangan Kerja / Laporan Kerja / Uraian Jobdesc) + KETERANGAN free text. Sheet import: Google Sheet CSV export per `gid` (merged 3-row headers, checkbox TRUE/FALSE, single-cell newline assessee list in "Kelompok Asesi" tab — split on line breaks, join on normalised name).
  - M1.5 Scale test: 500-file synthetic folder ingests without timeout; job survives a worker restart mid-run.
  - M1.6 **Triage (v1.1):** after ingest, the batch shows an unassigned queue — files with no assessee/assessor and assessees with no assessor — with a suggested mapping + confidence per item. Ketua Tim / LSP admin accepts a suggestion, picks a different target, or marks "not needed" with a reason; bulk-assign for rows sharing one suggestion. This is the screen that splits one flat shared folder (no per-assessor subfolders) across assessors. Rule: sheet import runs before ingest where a "Kelompok Asesi" sheet exists, so the name-join is available for suggestions; where no sheet exists, suggestions come from filename→person extraction only and every item starts unassigned.
- **Exit criteria:** the real 23-person "Persyaratan" folder (~160–185 files, est.) ingests end-to-end; completeness counts match a manual count of the sheet; every file has a status (`done/failed/unmatched`); no single HTTP request exceeds 10 s. **v1.1:** a synthetic one-folder/two-assessor split (QA ING-12) also passes — every file ends assigned, unassigned, or explicitly "not needed".
- **Dependencies / blockers:** Google Cloud project + Drive API key (see 11); a real folder to test against — the two live Drive links.

## 4. Phase 2 — Identity & decisions (Weeks 6–7)

**Goal:** the certificate name is right, and decisions are recorded auditably.

- **Milestones:**
  - M2.1 Identity check screen: KTP name (OCR/manual entry) vs APL.01 name vs surat-tugas name, side by side with diff highlight; "Nama tercetak di sertifikat" field; human Konfirmasi required; mismatch report. **No auto-merge, no auto-correct.** KTP image stored in a private Supabase Storage bucket (RLS: assessor role only, audit-logged access); NIK never stored in plain text alongside the name — see Technical Design (06) for the redaction rule.
    - **v1.2 — KTP OCR + name jury (D10).** (a) **OCR (this phase):** the KTP image is read by local Tesseract (`ind+eng`, already in the Phase 1 worker) as a background job; the extracted name text + per-field confidence are stored on the identity record. OCR runs locally — the KTP image never goes to an LLM. Low-confidence OCR is flagged amber ("Hasil OCR kurang yakin — periksa") and the jury proposes no name. (b) **Deterministic comparison (this phase):** normalised-name comparison + trigram similarity across the four sources (KTP OCR text, APL.01, surat tugas, ijazah) produces the evidence the jury reasons over. (c) **Jury reasoning (Phase 3, M3.7):** the LLM jury verdict itself ships once the Phase 3 LLM plumbing exists — until then the screen shows the deterministic comparison + the four sources and the assessor decides without a jury recommendation. The jury verdict, when it lands, is a recommendation only: `match` / `mismatch_resolved` (with a proposed name — always the KTP spelling, v1.3 D6) / `needs_human`. The certificate name becomes final only on assessor confirmation or override — never silently. **v1.2 note:** the jury is the AI agent inside the app acting as "jury" on the name verdict (Moza, 17 Nov 2026 23:45) — it judges the evidence; the assessor is the judge who confirms.
  - M2.2 AK.02 decision record: per-assessee, per-unit K/BK, evidence summary, assessor note; BK requires a note; every change writes an `audit_log` row (actor, timestamp, old → new).
  - M2.3 RLS + privacy hardening pass: cross-batch access tests, KTP-never-to-LLM test (redaction unit test with a synthetic NIK), export-log test.
  - M2.4 Batch roles: one batch, several assessors (real batch: 2 assessors, groups 11 + 12); each assessor sees their own group by default, LSP admin sees all.
- **Exit criteria:** identity mismatches for the real batch are listed and confirmable; a K/BK decision round-trips with a complete audit trail; privacy tests pass.
- **v1.3 — DECIDED (D6, Moza 2026-11-18 01:06):** certificate-name rule — The KTP (government ID) is the authority: the certificate name is the KTP name, verbatim. Surat tugas, APL.01, and ijazah are compared against the KTP, and any discrepancy resolves to the KTP spelling — surat tugas "Declan Rice P." vs KTP "Declan Rice Pangabean" → "Declan Rice Pangabean". OQ-06 is closed. (Was: an open question asking the LSP; see BNSP Forms Brief §8.6.)

## 5. Phase 3 — AI analysis, DIT route (Weeks 8–10)

**Goal:** the 04A pipeline from the user's interview prompt, as a versioned, auditable job — not a chat box.

- **Milestones:**
  - M3.1 LLM plumbing: Vercel AI SDK `generateObject` + Zod schemas; **provider-agnostic adapter (v1.4, D18 — Anthropic, OpenAI-compatible, Gemini, OpenRouter / OmniRouter / 9Router, Nvidia NIM, etc.; provider + base URL/gateway + model + key from the user's runtime Provider Settings, BYOK, free-first; no primary model)**; model ID + temperature (0 for grading/jury) + prompt version in config; every call stores provider + model + prompt version + raw output.
  - M3.2 DIT pipeline (two inputs, two artefacts — keep them separate):
    - (a) **Coverage matrix:** FR.IA.04A focus points × Terpenuhi / Sebagian / Belum Dibahas, evidence quotes from the presentation/transcript.
    - (b) **Gap questions:** per uncovered focus point, labelled TS / TMS / CMS / JRES / TrS, linked to the kelompok pekerjaan.
    - (c) **Question bank (separate artefact):** exactly the configured count (default 13), personalised from the presentation, STAR/scenario format, role-level adapted. Labelled in the UI as the user's 13-question bank — **not** the official FR.IA.04B.
    - (d) **Official FR.IA.04B** (presentation assessment: per-question Ya/Tdk, "memenuhi/belum memenuhi", K/BK recommendation) as its own form — assessor-filled, AI-assisted only for drafting questions. **v1.4 (D14 — OQ-02 ANSWERED, Moza 2026-11-18 01:18):** the LSP expects the official 04B form — verified from the real file (`research/skema-ak3u-2021-extracted.md`): 4 Kelompok Pekerjaan, 13 built-in questions (one per unit), Ya/Tidak per KUK, binary recommendation; its evidence is the DIT task + presentation. The form shows its built-in questions per KP with the DIT deck as evidence; the 13-question bank stays a separate artefact, always labelled "assessor's bank, not official FR.IA.04B".
  - M3.3 Readiness estimate: coverage % + strengths + critical gaps + recommendation. Recommendation values in the UI: Kompeten / Belum Kompeten as the decision — binary only. **v1.4 (D15 — OQ-03 CLOSED, Moza 2026-11-18 01:18):** there is no "Kompeten Bersyarat" outcome anywhere — not as a decision value, not as a readiness note, not as a report column. The scheme document §9.3.4 ("Kompeten" / "Belum Kompeten") and the 04B form itself (recommendation row offers only those two) confirm it; the v1.1 free-text-note allowance is removed.
  - M3.4 Prompt-injection guard: candidate text delimited as untrusted data; model output can never change a verdict without assessor sign-off.
  - M3.5 Blind comparison: run the pipeline on 5–10 real DIT + transcript pairs; an assessor scores the AI output against their own judgement before the default model is locked.
  - M3.6 **Completeness gate + prompt registry (v1.1):** (a) the DIT analyse endpoint enforces the gate — missing FR.IA.04A, transcript, or profile returns `incomplete_inputs` with `missing[]` and enqueues nothing; the UI shows the gate panel (doc 08 §4, doc 13 §7 v1.1). (b) The two assessor prompts are seeded as versioned templates (`dit-gap-analysis.v1`, `written-test-grading.v1`) from the verbatim sources in `research/prompts/` — adapted per doc 15 §4.4 v1.1 (Kompeten Bersyarat removed, bank labelled separately, model answers assessor-only) — with source SHA-256 hashes recorded in the registry. A prompt change creates a new version; old runs are never rewritten.
  - M3.7 **Name-jury reasoning (v1.2, D10):** the jury prompt (`name-jury.v1`, doc 15 §4.4 v1.2) runs on the Phase 2 comparison evidence: the four name strings + OCR confidence and nothing else (no NIK, no address, no phone, no KTP image — the jury exception to the pseudonym rule, stated explicitly in doc 15 §2.6 rule 30). Output is the Zod-validated verdict (`match` / `mismatch_resolved` / `needs_human`) + Bahasa Indonesia reasoning + one evidence span per compared name + a proposed certificate name only when the verdict is `mismatch_resolved` (composed only of name tokens present in the sources — the jury never invents a name). Below the configured OCR-confidence floor the jury returns `needs_human` with no proposed name. The verdict is stored with prompt version + model + raw output like every other AI run, and is a recommendation only.
- **Exit criteria:** all 5–10 test candidates produce a complete matrix + 13 questions (count assertion passes in CI); every output carries model + prompt version + evidence quotes; assessor sign-off on quality. **v1.1:** the gate refuses an analysis with missing inputs (QA DIT-02) and a prompt-version replay leaves old runs unchanged (QA PRM-01).
- **Risks:** small-model drift (12/14 questions, mixed language) — mitigated by Zod count validation + retry-once + `needs_manual_review` on failure.

## 6. Phase 4 — AI grading & similarity (Weeks 11–13)

**Goal:** written-test grading the assessor can defend, and similarity flags that name pairs without accusing anyone.

- **Milestones:**
  - M4.1 Written-test grading (FR.IA.06): per-LSP form-version mapping resolves which file is the key (06B under MUK 2023 — configurable); deterministic first (normalised exact match, keyword/coverage check vs key), LLM only for partial-credit semantic judgement; per-question `correct / partial / incorrect` + master-vs-student spans + explanation in Bahasa Indonesia; assessor confirms per item. **The 06 form itself requires professional judgement — AI recommends, assessor decides.**
  - M4.2 Similarity engine (layered, deterministic first): normalised n-gram/Jaccard → TF-IDF + cosine (per question and per document, pairwise within batch) → embeddings + cosine via pgvector (paraphrase layer; threshold per question type, short answers reported separately) → LLM summary only. Store top-N pairs per question with shared spans highlighted. Shared unique errors called out explicitly. **v1.4 (D19):** flags use per-scope **numeric thresholds with evidence details** (spans, shared unique errors) — the threshold values are config and **UNCONFIRMED** (calibration sets them; no number is asserted here). The qualitative status (Bersih / Waspada) stays as the human-facing summary alongside the numeric flag.
  - M4.3 Similarity report UI: pairs, question numbers, overlap scores, shared spans, verdict selector (Kebetulan / Perlu Ditinjau / Indikasi Menyalin) — flag only, never auto-fail, never auto-merge identities. Names always exact, never normalised for display.
  - M4.4 Calibration test: a known copy-paste pair, a paraphrase pair, and an unrelated pair (see QA 10) — thresholds tuned until the three separate cleanly.
